# Channel-to-Referral Integration

## Problem

USSD, SMS, and voice each let a citizen reach a "connect me to support" point,
but today that only ever hands back a raw `SupportService.phone_number` for
the citizen to dial or text themselves. Nothing on the partner-portal side
(`apps.partners`, `apps.referrals`) ever learns that contact happened, so a
partner organisation can't track or follow up on citizens who came in through
these channels.

Two pieces already exist for the web citizen flow but are unused by the
channels:

- `PublicPartnerMatchAPIView` (`apps/partners/views.py`) — scores and filters
  verified, `accepting_referrals` partner organisations by rights category,
  district, language, and support channel.
- `CitizenReferralCreateAPIView` (`apps/referrals/views.py`) — creates a
  `Referral` given a chosen organisation, with citizen consent as a hard
  gate (`citizen_consent_to_share` must be `True`).

This design wires USSD, SMS, and voice into that same matching + referral
machinery, in-process (no HTTP self-calls), following the existing pattern
where channels call `apps.rights.services` directly for latency reasons.

## Scope

- **In scope:** USSD, SMS, and voice, for situations where
  `Situation.risk_level != "high_risk"`.
- **Out of scope:** `high_risk` situations (domestic violence, sexual
  harassment) keep today's direct-dial/text-out behavior unchanged — no
  consent step, no matching, no referral. Speed matters more than case
  tracking in a crisis, and the `citizen_consent_to_share` gate would add
  friction to an already time-sensitive path.
- **Out of scope:** `apps.chat` / `apps.legal_knowledge` — separate web-only
  surface, not touched by this design.

## Architecture

### 1. Extract the matching logic into a reusable service

`apps/partners/services.py` (new file):

```python
def find_matching_organisations(category, district, language, channel):
    """
    Returns verified, accepting-referrals PartnerOrganisations matching
    the given rights category/district/language/support-channel, scored
    and sorted highest-first. Pure function - no HTTP, no request object.
    """
```

This is the existing filter/score loop currently inline in
`PublicPartnerMatchAPIView.get()` (`apps/partners/views.py`, roughly lines
1039-1198), moved out unchanged. `PublicPartnerMatchAPIView` becomes a thin
wrapper: parse query params, call the service, serialize, return. No change
to the public API's behavior or response shape.

### 2. New referral-creation service for channels

`apps/referrals/services.py` (new file):

```python
def create_citizen_referral(phone_number, situation_slug, district, language, channel):
    """
    Attempts to create a Referral for a citizen contacting via USSD/SMS/
    voice. Returns the created Referral, or None if no eligible partner
    organisation matches (caller should fall back to the raw support
    phone number in that case).
    """
```

Behavior:

1. Look up the `Situation` by slug; take the first `RightsTopic` linked via
   `SituationRightsTopic`, ordered by `SituationRightsTopic.id` ascending
   (creation order — the model defines no other ordering), as the match
   "category" (its `slug`, matching the string format already used in
   `PartnerServiceConfiguration.rights_categories`, e.g.
   `"work-employment"`). A situation with multiple linked topics only gets
   matched against the first one; this is a deliberate simplification, not
   an oversight.
2. Call `find_matching_organisations(category=topic.slug, district=district,
   language=language, channel=channel)`.
3. If empty → return `None`.
4. If not empty → take the top-scored match and create:
   - `Referral(organisation=..., rights_topic=topic, contact_phone=phone_number,
     district=district, language=language, preferred_support_channel="phone",
     citizen_consent_to_share=True, summary=<auto-generated one-liner, e.g.
     "SMS referral: citizen reported 'Facing eviction'">, status="new",
     shared_at=now(), reference=<generated>)`
   - `ReferralStatusHistory(referral=referral, from_status="", to_status="new",
     changed_by=None, note="Referral created via sms.")`
5. Return the created `Referral`.

Reference generation (`f"SY-REF-{uuid4().hex.upper()}"`) is currently
duplicated in `ReferralCreateAPIView` and `CitizenReferralCreateAPIView`;
this design adds a third caller, so it's worth pulling into a single
`Referral.generate_reference()` staticmethod on the model and having all
three call sites use it.

### 3. Schema change: `Referral.contact_phone`

The `Referral` model has no phone field today — the web flow doesn't need
one since the citizen is present live in the browser. USSD/SMS/voice are
asynchronous; a partner organisation cannot follow up without a number.

Add:

```python
contact_phone = models.CharField(max_length=50, blank=True)
```

with a migration. Populated from the channel's known `phone_number` when a
referral is created via `create_citizen_referral`; left blank for
web-originated referrals (`CitizenReferralCreateAPIView` doesn't set it).

## Per-channel flow

Applies identically to USSD, SMS, and voice, triggered at each channel's
existing "connect me to support" point, gated by
`Situation.risk_level != "high_risk"`:

1. **Consent prompt** (explicit, channel-native — asking for support does
   *not* imply consent):
   - *SMS*: "An organisation may be able to help directly. Reply YES to let
     them contact you, or reply NO for just the number."
   - *Voice*: new IVR digit choice before the existing dial-out ("Press 1 to
     have an organisation call you back, press 2 to get the number now").
   - *USSD*: new menu option on the support-contacts screen ("1. Connect me
     with an organisation").
2. **District collection**, only if consent = yes (nothing today tracks
   district on any channel):
   - *SMS* / *USSD*: free-text reply ("Which district are you in?").
   - *Voice*: reuse the existing recording → Whisper transcription pipeline
     (`apps/channels/voice/transcription.py`) already used elsewhere in the
     voice flow, rather than building a DTMF district list.
3. **Referral attempt** — on receiving the district, call
   `create_citizen_referral(phone_number, situation_slug, district, language,
   channel="phone")`.
   - USSD supplies `language` from `UssdSession.language` (already tracked).
   - SMS and voice track no language today; default `language="en"` for
     matching purposes. Pre-existing gap, not addressed by this design.
4. **Reply to citizen**:
   - Match found → "You're referred to {org name}. Reference {reference}.
     They may call you on this number."
   - No match, consent declined, or unrecognized district reply → fall back
     to exactly today's behavior: the raw `SupportService` phone number, no
     `Referral` created.

### New session state

Each channel needs a small amount of new state to track "mid-consent" /
"mid-district-collection", using a single field rather than several
booleans (mirroring the existing `pending_safety_check` pattern on
`SmsContext`, but generalized so USSD/voice don't need their own analogues):

- `SmsContext.pending_referral_step` — `CharField`, blank or one of
  `"consent"`, `"district"`.
- `VoiceSession` and `UssdSession` already have a general-purpose `state`
  field driving their state machines; the new consent/district steps become
  additional `state` values (`awaiting_referral_consent`,
  `awaiting_referral_district`) following the existing pattern for each.

## Error handling

Every failure mode degrades to today's existing behavior — the citizen is
never left without a contact:

- No matching organisation → fallback raw phone number message (unchanged
  from today).
- Consent declined, or reply doesn't match a recognized yes/no/digit answer
  → same fallback, no retry loop.
- District reply doesn't resolve to anything usable → same fallback rather
  than re-prompting indefinitely.
- `Referral`/`ReferralStatusHistory` creation errors (e.g. DB issue) →
  caught and logged; the channel still delivers the raw phone number.
- `high_risk` situations never enter this flow at all, so it introduces no
  new failure surface on the crisis path.

## Testing

Extends existing suites in the same style used for the safety-check-in and
SMS AI-classification work:

- `apps/partners/tests.py` — adapt existing `PublicPartnerMatchAPIView`
  tests to call `find_matching_organisations` directly where appropriate;
  behavior is relocated, not changed.
- `apps/referrals/tests.py` — new tests for `create_citizen_referral`: match
  found, no match, and confirming it is never invoked for `high_risk`
  situations.
- `apps/channels/{sms,voice,ussd}/tests.py` — new tests per channel for the
  consent → district → referral happy path, consent declined, and an
  unrecognized district reply, following the pattern of the existing
  safety-check-in tests.

## Out of scope / explicitly deferred

- Broadening the match when no district-specific organisation is found
  (e.g. falling back to any nationwide organisation regardless of
  language) — the fallback is always "give the raw phone number," never an
  automatically broadened match.
- Collecting/storing a language preference for SMS or voice sessions.
- Any change to the `high_risk` / crisis contact path.
- Wiring `apps.chat` or `apps.legal_knowledge` into the channels.
